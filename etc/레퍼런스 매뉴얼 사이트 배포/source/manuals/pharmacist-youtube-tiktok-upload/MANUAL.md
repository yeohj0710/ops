# 약사님들 유튜브·틱톡 영상 업로드

- **부르는 말**: 약사님들 유튜브 틱톡 업로드, 유튜브 틱톡 영상 올려줘, 약사 영상 예약 업로드, 유튜브·틱톡 업로드 업무
- **미리 허가**: 유튜브와 틱톡 업로드, 플랫폼 예약 저장
- **런너**: codex (Claude는 준비와 기록까지만. 아래 "런너를 고르는 기준"을 보라)
- **제어층**: L1 로 준비·기록, L3 으로 로그인된 업로드 화면
- **한 번에 걸리는 시간**: 영상 1편당 5~10분, 대량 예약은 영상 수와 처리 시간에 따라 30분 이상

---

## 무엇을 만드는 업무인가

약사님 인스타그램 릴스 중 유튜브와 틱톡에 아직 없는 영상만 골라 같은 계정으로 올리고, 플랫폼의 **자체 예약 입력란**에서 하루 한 편씩 예약한다. 영상·제목·캡션은 `<DRIVE>/여형준님/28 유튜브 틱톡 업로드/` 아래에 계정별 날짜 폴더로 남기고, 플랫폼 ID·예약 시각·처리 결과는 `logs/`에 남긴다.

이 매뉴얼은 특정 약사나 특정 날짜에만 맞춘 절차가 아니다. 각 인스타그램 프로필과 대응하는 유튜브 채널·틱톡 계정을 입력으로 받아 같은 순서로 처리한다.

## 실행 계약

사용자가 이 업무를 호출하면 준비, 중복 확인, 업로드, 플랫폼 자체 예약, 결과 검증, 업로드 기록까지 한 번에 실행한다. 업로드 버튼과 예약 저장은 이 업무에 포함된 승인으로 보고 다시 묻지 않는다. 매뉴얼 밖의 대상 게시, 비밀번호·CAPTCHA 입력, 매뉴얼 밖 결제, 되살릴 수 없는 삭제만 사람에게 묻는다.

예약이 이미 지나갔거나 계정 상태가 달라져 같은 실행에서 안전하게 고칠 수 없으면 그 영상만 보류하고, 정확한 원인과 다음 가능한 시각을 로그와 보고에 남긴다. 다른 계정의 독립 작업은 계속한다.

## 런너를 고르는 기준

**이 업무의 런너는 Codex다.** 업로드와 예약은 브라우저가 영상을 읽어야 넘어가는데,
Claude가 쓰는 크롬 익스텐션은 **항상 배경 탭**을 만든다. 배경 탭은 `visibilityState`가 `hidden`이라
크롬이 미디어 로딩을 멈추고, 유튜브는 "예기치 않은 문제가 발생했습니다", 틱톡은 업로드 화면에서 멈춘다.
Codex 인앱 브라우저는 화면에 실제로 그려지므로 이 벽이 없다. 260821 성공 기록도 Codex 경로다.

Claude로 이 업무가 불렸을 때는 이렇게 나눈다.

- Claude가 하는 것: 인스타 신규 릴스 확인과 추출, 폴더와 `title.txt`, `caption.txt` 정리,
  플랫폼 목록과 대조한 중복 확인, `known_items.txt`와 `state.json` 갱신, 보고 파일 작성
- Codex가 하는 것: 유튜브와 틱톡 업로드, 플랫폼 자체 예약, 업로드 기록 갱신

**사용자 창을 뺏어서 우회하지 마라.** 창을 앞으로 세우거나 키를 보내 탭을 넘기는 짓은
사용자가 쓰던 화면을 망가뜨린다. 260907에 실제로 작업을 방해해서 중단당했다.
Claude에서 업로드 단계에 닿으면 준비까지만 끝내고 **Codex에 넘길 프롬프트를 만들어 준다.**

## 준비물

- `<DRIVE>`가 연결되어 있고, `여형준님/28 유튜브 틱톡 업로드/`에 계정 폴더와 `logs/`가 있다.
- 인스타그램 원본 계정과 대응하는 유튜브 채널·틱톡 계정의 로그인 세션이 살아 있다.
- 기존 인스타 미디어 추출기에서 원본 릴스의 MP4와 캡션을 꺼낼 수 있다. 도구가 바뀌어도 절차는 `L1로 추출 → 파일 검증`으로 유지한다.
- 기본 예약 시각은 한국 시간(Asia/Seoul) **18:15**다. 오늘 18:15가 지났으면 오늘 영상만 19:15를 쓴다. 19:15도 지났다면 과거 시각을 억지로 저장하지 말고 해당 영상만 보류해 보고한다.

## 계정과 입력 매핑

1. 인스타그램 프로필, 출력 폴더, 유튜브 채널, 틱톡 계정을 표로 먼저 확정한다. 이름·프로필 사진·URL만 보고 추측하지 않는다.
2. 업로드 화면의 채널명/프로필명과 계정 폴더가 일치하는지 확인한다. 계정이 다르면 게시하지 말고 계정 전환 후 업로드 화면을 다시 연다.
3. 유튜브 두 채널과 틱톡 대상 계정이 각각 별도 로그인일 수 있다. 한 탭의 로그인 상태를 다른 탭에 재사용한다고 가정하지 않는다.

## 폴더와 날짜 규칙

계정 폴더 아래에 `YYMMDD 제목` 폴더를 만든다.

```text
<DRIVE>/여형준님/28 유튜브 틱톡 업로드/
  <약사 계정 폴더>/
    260901 영상 제목/
      video.mp4
      title.txt
      caption.txt
  logs/
    state.json
    known_items.txt
    youtube_upload_ledger.txt
    tiktok_upload_ledger.txt
```

- 날짜 코드는 **실제 달력 날짜**다. `260831` 다음은 `260901`이며 `260832`, `260833`, `260834`를 만들지 않는다.
- 하루 한 편 예약은 계정별 규칙이다. 오약과 제씨가 각각 대상이면 각 계정의 다음 날짜를 따로 계산한다.
- 기존 폴더가 있다는 이유만으로 미업로드로 보지 않는다. 플랫폼 원본 목록과 대조한 뒤 이미 올라간 항목은 큐에서 제외한다.
- 폴더를 삭제하거나 이름을 바꾸기 전에 플랫폼 ID와 제목을 다시 대조한다. 중복 정리는 되살릴 수 없는 삭제이므로 매뉴얼에 없는 삭제는 사람에게 묻는다.

## 절차

### 1. 로컬 상태와 미처리 큐를 읽는다 (L1)

1. `logs/state.json`, `logs/known_items.txt`, 유튜브·틱톡 업로드 기록을 읽는다.
2. 계정별 대상 폴더에서 `video.mp4`, `title.txt`, `caption.txt`가 모두 있고 MP4 크기가 0보다 큰지 확인한다.
3. 날짜 범위에 맞는 폴더만 센다. 오래된 원본 폴더 전체를 세어 준비 수량으로 보고하지 않는다.
4. 업로드 기록에는 처리된 항목을 `계정|폴더|플랫폼|상태` 단위로 유일하게 기록한다. 수정 이력은 지우지 말고 `deleted_for_correction` 같은 상태로 남긴다.

**성공 판정:** 계정별 미처리 후보, 이미 업로드된 후보, 파일 누락 후보가 분리되어 있고 다음 폴더가 하나로 결정된다.

### 2. 인스타그램 릴스를 추출하고 파일을 정리한다 (L1)

1. 지정된 인스타그램 프로필의 릴스를 최신순으로 확인한다.
2. 기존 미디어 추출기로 MP4와 캡션을 받는다. 다운로드가 끝난 뒤 영상이 재생되고 세로 비율인지 확인한다.
3. `<DRIVE>/여형준님/28 유튜브 틱톡 업로드/<계정>/<YYMMDD 제목>/`에 `video.mp4`, `title.txt`, `caption.txt`를 저장한다.
4. `title.txt`에는 유튜브 제목을, `caption.txt`에는 인스타그램 캡션 전문을 저장한다. 틱톡은 별도 제목 칸을 쓰지 않고 `caption.txt`를 그대로 사용한다.

**성공 판정:** 세 파일이 모두 존재하고 MP4를 재생할 수 있으며, 캡션 줄바꿈·해시태그가 보존된다.

### 3. 이미 업로드된 항목을 플랫폼에서 제외한다 (L1 → L3)

1. 업로드 기록만 믿지 말고 유튜브 두 채널의 콘텐츠 목록과 틱톡 콘텐츠 목록에서 제목·썸네일·게시일·원본 ID를 대조한다.
2. 제목이 조금 달라도 같은 영상 ID, 같은 원본 URL, 같은 영상 길이와 썸네일이면 이미 처리된 항목으로 본다.
3. 틱톡 콘텐츠 목록이 조회수/성과순으로 정렬되어 최신 날짜가 위에 없을 수 있다. 검색이나 게시물 ID로 확인한다.
4. 중복으로 새 게시물을 만들지 않는다. 같은 실행 중 중복을 만들었다면 두 ID와 원인을 업로드 기록에 기록하고, 삭제는 사용자가 명시한 경우에만 한다.

**성공 판정:** 각 플랫폼의 실제 미업로드 후보만 남고, 이미 공개·예약된 영상은 업로드 큐에서 빠진다.

### 4. 유튜브에 업로드하고 자체 예약한다 (L3)

계정별로 한 편씩 끝내고 다음 편으로 간다.

1. 로그인된 유튜브 채널의 헤더 이름을 확인한다.
2. `동영상 업로드`에서 `video.mp4`를 고른다. 제목은 `title.txt`, 설명은 `caption.txt` 형식에 맞춰 넣는다.
3. 아동용 여부 등 기본 설정을 기존 채널 기준과 맞춘다.
4. 공개 상태에서 **유튜브 화면의 `예약`**을 선택한다. 외부 OS 스케줄러나 별도 자동화 스케줄러에 등록하지 않는다.
5. 날짜는 실제 달력 날짜, 시간은 `18:15`(오늘 예외는 `19:15`), 시간대는 `Asia/Seoul`로 입력한다.
6. 예약 대화상자에 `오전 12:00` 또는 `00:00`이 기본으로 남아 있지 않은지 확인한 뒤 저장한다.
7. 저장 직후 콘텐츠 목록에서 제목·상태 `예약됨`·날짜를 확인한다. 목록에 시간이 안 보이면 영상 편집 화면의 `동영상 공개 상태 수정` 대화상자를 열어 시간을 다시 확인한다.
8. 유튜브 영상 ID와 예약 날짜·시간을 `youtube_upload_ledger.txt`에 즉시 기록한다.

**성공 판정:** 계정 헤더가 대상 채널과 일치하고, 해당 영상의 유튜브 자체 상태가 `예약됨`이며 예약 시각이 업로드 기록과 같다. 처리 중이면 `scheduled_processing`으로 기록하고 완료될 때까지 확인한다.

### 5. 틱톡에 업로드하고 자체 예약한다 (L3)

1. 로그인된 TikTok Studio에서 대상 계정명을 확인한다. 인앱 브라우저에서 로그인 화면이 나오면 로그인된 Chrome 세션으로 전환하고, 로그아웃하지 않는다.
2. 동영상 업로드에서 `video.mp4`를 고른다.
3. 제목 칸은 만들지 않는다. `caption.txt`의 캡션을 그대로 입력하고, 해시태그·줄바꿈을 확인한다.
4. TikTok Studio의 자체 예약 기능에서 날짜와 시간을 입력한다. 기본은 `18:15`, 오늘 예외는 `19:15`다.
5. 예약 게시물 목록에서 게시물 ID, 캡션 첫 문장, 날짜·시간을 확인한다. 성과순 목록의 첫 항목만 보고 최신 처리 여부를 판단하지 않는다.
6. 게시물 ID와 예약 날짜·시간을 `tiktok_upload_ledger.txt`에 즉시 기록한다.

**성공 판정:** 계정명이 대상과 일치하고, 캡션이 인스타그램 원문과 맞으며, TikTok Studio에 예약 게시물과 시간이 보인다.

### 6. 매 건마다 체크포인트를 남긴다 (L1)

1. 한 편이 끝날 때마다 `state.json`의 계정별 `scheduled`, `queued`, `draft`, 오류 수를 갱신한다.
2. `known_items.txt`에는 성공·스킵·실패·수정 항목을 모두 한 줄씩 추가한다.
3. 수정 업로드는 기존 기록을 덮지 말고 새 ID와 수정 사유를 추가한다.
4. 플랫폼의 실제 예약 수와 업로드 기록의 **유일한 활성 항목 수**를 비교한다. 과거 수정 기록을 현재 대기 수에 중복 계산하지 않는다.

### 7. 최종 보고를 남긴다 (L1)

`<DRIVE>/에이전트/보고/YYYY-MM-DD-약사-유튜브틱톡.md`에 계정별 처리 수, 스킵·중복·실패, 예약 날짜·시간, 유튜브·틱톡 ID, 남은 작업을 적는다. 외부 공유 링크는 만들지 않는다.

- [ ] (기계) 유튜브·틱톡 업로드 기록에 계정·폴더·상태·예약 시각·플랫폼 ID가 있고 활성 항목이 중복되지 않는다

## 알려진 함정

- **기존 폴더가 있는데 미업로드로 보임** → 폴더 존재는 업로드 증거가 아니다 → 유튜브·틱톡 실제 콘텐츠 목록과 ID·제목을 대조한다.
- **`260834` 같은 폴더가 생김** → 일련번호처럼 날짜를 증가시켰다 → 실제 달력으로 계산하고 `260831` 다음은 `260901`로 만든다.
- **유튜브에 00:00 예약이 생김** → 예약 입력란의 기본값을 덮지 않았다 → 날짜·시간을 다시 입력하고 저장 직전 표시값을 읽는다.
- **외부 스케줄러에 등록했는데 유튜브 예약이 다름** → 플랫폼 자체 예약 입력란을 건너뛰었다 → 유튜브 업로드 공개 상태의 `예약`에서 직접 저장한다.
- **오늘 영상이 이미 공개됨** → 18:15가 지난 뒤 상태를 확인했다 → 현재 시각을 먼저 읽고, 과거 시각을 소급 입력하지 않는다. 이미 공개된 영상은 새 시간을 임의로 만들지 말고 보류 사유를 기록한다.
- **유튜브 목록에는 날짜만 보임** → 목록이 시간까지 표시하지 않는다 → 영상 편집 화면의 공개 상태 수정 대화상자에서 시간을 확인한다.
- **틱톡 최신 영상이 빠짐** → 목록이 성과순·가상 스크롤로 보인다 → 캡션 검색, 게시물 ID, 날짜 필터를 함께 사용한다.
- **틱톡에 제목을 따로 넣으려 함** → 유튜브 입력 구조를 그대로 적용했다 → 틱톡에는 제목을 만들지 않고 인스타 캡션만 넣는다.
- **엉뚱한 약사 계정에 게시됨** → URL·탭 위치·프로필 사진만 보고 계정을 판단했다 → 업로드 화면 헤더의 계정명을 게시 직전에 확인한다.
- **내장 브라우저에서 로그인이 안 됨** → 로그인 세션이 내장 브라우저와 분리되어 있다 → 로그인된 L3 브라우저 세션을 사용하고 로그아웃·비밀번호 직접 입력은 하지 않는다.
- **좁은 화면 때문에 업로드가 안 된다고 판단함** → 실제 원인은 계정 세션·모달·처리 대기일 수 있다 → 화면 크기를 먼저 바꾸지 말고 계정명, 버튼 상태, 처리 상태를 읽는다.
- **예약 버튼 클릭이 안 됨** → 동적 웹 요소가 다시 그려져 기존 선택자가 낡았다 → 현재 DOM의 접근 가능한 이름으로 다시 찾고, 같은 동작을 두 번 실패하면 안전한 대체 경로를 기록한다.
- **TikTok 시간은 맞는데 캡션이 다름** → 자동 번역·복사 과정에서 줄바꿈이나 해시태그가 변했다 → `caption.txt` 원문을 붙여 넣고 게시 전 첫 문장·끝 해시태그를 대조한다.
- **수정 기록이 실제 수량보다 많아짐** → 삭제·재업로드 기록을 현재 수량에 합쳤다 → 과거 수정 행은 보존하되 활성 ID만 유일하게 센다.
- **상태 파일에 `queued`가 남음** → 계정별 상태를 갱신하지 않고 상위 요약만 읽었다 → 계정별 업로드 기록과 실제 플랫폼 목록을 기준으로 요약 수를 다시 계산한다.
- **한 계정만 처리하고 끝냄** → 여러 계정의 작업을 하나의 탭·하나의 큐로 취급했다 → 계정별 체크포인트를 남기고 모든 지정 계정을 순회한다.

- **배경 탭에서는 영상 메타데이터를 못 읽는다 (260907 실측)** → 크롬 확장이 만드는 탭은 창을 앞으로 세워도 계속 배경 탭이고 `document.visibilityState`가 `hidden`이다 → 유튜브는 파일을 받은 직후 "예기치 않은 문제가 발생했습니다"로 떨어지고 틱톡도 같은 단계에서 막힌다. 판정은 빈 페이지의 `input[type=file]`에 같은 MP4를 넣고 `URL.createObjectURL`로 video를 만들어 `loadedmetadata`를 기다리는 것이다. 9초를 기다려도 안 오면 배경 탭이다.
- **탭을 활성으로 바꾸는 방법이 확장에 없다 (260907 실측)** → `tabs_create_mcp`로 빈 탭을 만들어도 그 탭까지 배경으로 생기고 창이 앞으로 나오지 않는다. `SetForegroundWindow`로 창을 올려도 그 탭이 창의 활성 탭이 아니면 소용없다. `outerWidth`가 0이면 그 탭은 한 번도 그려진 적이 없다는 뜻이다.
- **SendKeys로 탭을 순회하지 마라 (260907)** → `Ctrl+Tab`을 보내면 사용자가 지금 타이핑하는 창에 그대로 들어간다. 260907에 사용자가 작업 중에 키가 눌려 중단시켰다. 사람에게 탭을 한 번 눌러 달라고 하고, 그 창을 `SetWindowPos`의 `SWP_NOACTIVATE`로 화면 한쪽에 세워 포커스를 뺏지 않고 계속 보이게 둔다.
- **yt-dlp의 `--cookies-from-browser chrome`이 안 된다** → 크롬이 떠 있어 DB가 잠기고 App-Bound Encryption까지 걸린다 → 인스타 릴스는 릴스 페이지의 스크립트에서 `video_versions`를 파싱해 최고 화질 URL과 캡션을 뽑고, 그것을 Blob으로 만들어 `a[download]`로 내려받아 파일로 옮긴 뒤 L1에서 그 URL로 내려받는다. 확장 JS의 반환값은 쿼리스트링이 있으면 막히므로 URL을 화면으로 돌려받지 말고 파일로 떨군다.
- **탭이 그룹에서 빠진다** → 그룹의 다른 탭을 닫으면 남은 탭이 그룹에서 빠져 `Tab is not in Claude's tab group`이 뜬다 → `tabs_context_mcp`를 `createIfEmpty`로 다시 불러 그룹을 세우고 탭 id를 다시 받는다.

- **유튜브가 파일을 받자마자 오류를 냄인데 화면 문제가 아님 (260907 실측)** → `POST https://upload.youtube.com/upload/studio?authuser=N`이 `401 {"status":"STATUS_REJECTED","rejectionReason":"REJECTED_NOT_AUTHENTICATED"}`을 돌려준다 → 그 구글 계정의 업로드 세션이 죽은 것이다. 재현과 판정은 스튜디오 페이지에서 순수 fetch로 그 주소를 직접 찔러 보면 된다. 읽기(채널 목록, 콘텐츠 목록)는 멀쩡히 되므로 로그인 여부만 보고 판단하면 안 된다. `ServiceLogin`, `youtube.com/signin`으로 세션을 다시 받아도 안 풀리면 사람이 그 계정에 다시 로그인해야 한다.
- **실패 원인을 화면에서 못 읽음** → 업로드 대화상자는 "예기치 않은 문제가 발생했습니다"만 보여준다 → 파일을 넣기 전에 `XMLHttpRequest.prototype.open/send`와 `window.fetch`를 가로채 `upload`가 들어간 요청의 상태와 응답 본문을 모아 두면 진짜 이유가 한 번에 나온다.
- **배경 탭이라 영상이 안 붙음** → 확장이 만드는 탭은 항상 배경 탭이다 → 드라이브 `에이전트/능력/화면과로그인.md`의 "배경 탭에서는 영상이 안 붙는다" 절을 그대로 따른다. 실제 클릭으로 팝업 창을 띄우고, 여는 쪽 탭에서 `DataTransfer`로 파일을 넘긴다.

## 사람에게 물어야 하는 지점

- 계정 매핑이 파일·플랫폼 화면 어디에도 없을 때
- 오늘 기본 시각과 예외 시각이 모두 지나서 새 예약일을 정해야 할 때
- 이미 공개된 영상을 비공개·삭제·재업로드해야 할 때
- 매뉴얼에 없는 결제, 메시지, 공유 대상, 삭제가 필요한 때
