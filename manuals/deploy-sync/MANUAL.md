# 배포 사이트 최신화

- **부르는 말**: 사이트 최신화해줘, 배포 동기화, 사이트 다 올려줘, 데이터 동기화하고 배포해줘, 뒤처진 사이트 있나, 배포 상태 봐줘, 사용량 정리해줘, 노션 배포 링크 갱신
- **런너**: either
- **제어층**: L1 로 전부 한다. 노션 갱신만 L1 이 안 되면 L3
- **한 번에 걸리는 시간**: 밀 것이 없으면 5분, 대여섯 개 밀면 20분에서 40분

---

## 쉬운 설명

**쓰는 상황.** 사이트를 여러 개 띄워 놓고 돌리는데, 데이터는 루프가 계속 채우고 있다.
며칠 지나면 화면에 뜨는 숫자가 실제보다 뒤처진다. 그걸 한 번에 맞추는 업무다.
겸사겸사 Vercel 사용량을 먹는 자리도 찾아내고, 노션 링크 페이지도 다시 적는다.

**시키는 말.** "사이트 최신화해줘" 한 문장이면 된다.

**진행 순서.** 무엇이 뒤처졌는지 세고, 뒤처진 것만 밀고, 무거운 자리를 찾고, 노션을 다시 적는다.

**결과물.** 뒤처진 사이트가 최신이 되고, 노션 페이지가 오늘 상태로 바뀌고,
사용량을 먹는 자리 목록이 보고에 남는다.

---

## 무엇을 만드는 업무인가

끝났을 때 이렇게 되어 있어야 한다.

1. `registry.json` 에 등록된 사이트 중 **뒤처진 것이 없다.** 밀지 못한 것은 이유가 적혀 있다
2. `<OPS>/work/deploy-sync/` 에 `scan.json`, `run.json`, `weight.json` 이 있다
3. 노션 "각종 프로젝트 배포 링크" 페이지가 **오늘 시각과 오늘 숫자**로 바뀌어 있다
4. 사용량을 먹는 자리가 보고에 숫자로 적혀 있다. 고칠 수 있는 것은 고쳐져 있다

## 실행 계약

사용자가 이 업무를 호출하면 이 매뉴얼의 절차와 완료 검사를 한 번에 실행한다.
**중간에 묻지 않는다.** 배포와 빌드는 이 업무의 내용이라 이미 승인된 것이다.

멈추고 묻는 것은 넷뿐이다.

- 등록 안 된 사이트를 새로 배포해야 할 때
- Vercel 프로젝트를 **지워야** 할 때 (되살릴 수 없다)
- 커밋 3만 개를 한 번에 push 하는 것처럼 되돌리기 무거운 일
- 봉인된 졸업논문 사이트(`nutrition-safety-engine`, `otc-nutrient-safety-engine`)의 숫자를 바꿔야 할 때

## 준비물

- Vercel CLI 가 로그인돼 있어야 한다. `npx vercel whoami` 로 확인한다.
  이름이 안 나오면 `npx vercel login` 은 대화형이라 사람이 한 번 해야 한다
- 노션 단계는 노션을 만질 수 있는 런너만 한다. 없으면 본문 파일만 만들고 그 사실을 보고에 적는다
- 그림을 줄이려면 `ffmpeg` 가 있어야 한다. 없으면 목록만 나오고 넘어간다

## 절차

### 1. 무엇이 뒤처졌는지 센다 (L1)

```bash
node "<OPS>/manuals/deploy-sync/scan.mjs"
```

읽기만 한다. 아무것도 배포하지 않는다. 다 세면 표가 뜨고 `work/deploy-sync/scan.json` 이 생긴다.

판정이 다섯 가지다.

| 판정 | 뜻 | 무엇을 하나 |
| --- | --- | --- |
| 최신 | 올린 것이 로컬보다 새것이다 | 아무것도 안 한다 |
| 배포 필요 | 데이터나 빌드 산출물이 마지막 배포보다 새것이다 | 민다 |
| 루프 멈춤 의심 | 스스로 올리는 사이트인데 여섯 시간 넘게 조용하다 | 손으로 한 번 민다 |
| 휴면 | 두 주 넘게 아무도 안 건드렸다 | **손대지 않는다** |
| 사람이 부를 때만 | 자동 배포에서 뺀 것이다 | 사람이 이름을 대야 민다 |

**휴면을 되살리지 마라.** 죽어 있는 사이트는 고장이 아니라 안 쓰는 것이다.
되살리면 빌드 시간과 함수 실행시간만 나간다. "다 확인해봐" 가 "다 되살려봐" 는 아니다.

### 2. 뒤처진 것만 민다 (L1)

```bash
node "<OPS>/manuals/deploy-sync/run.mjs"
```

`scan.json` 에 적힌 할 일을 순서대로 친다. 동기화, 빌드, 배포 순이다.
한 프로젝트가 실패해도 멈추지 않는다. 그 줄만 실패로 적고 다음으로 간다.

무엇을 칠지 먼저 보고 싶으면 `--dry-run`, 하나만 밀려면 `--only <프로젝트>` 를 붙인다.

다 밀었으면 **다시 센다.** 이게 배포됐는지 확인하는 유일한 방법이다.

```bash
node "<OPS>/manuals/deploy-sync/scan.mjs"
```

"배포 필요" 가 남아 있으면 그 프로젝트만 다시 민다. 두 번 해도 안 되면 그 건은 보고에 적고 넘어간다.

### 3. 사용량 먹는 자리를 찾는다 (L1)

```bash
node "<OPS>/manuals/deploy-sync/weight.mjs"
```

올리는 payload 크기, 큰 그림, 캐시 설정, 크론, 짧은 revalidate 를 본다.
`--deploys` 를 붙이면 프로젝트마다 최근 배포 횟수까지 센다. 조회가 하나씩 더 드니 필요할 때만 붙인다.

찾은 것 중 **고쳐도 되는 것은 고친다.**

- **큰 그림**: `node "<OPS>/manuals/deploy-sync/shrink.mjs" --only <프로젝트> --apply`
  파일 이름을 그대로 두고 폭 1920 으로 맞춰 다시 굽는다. 원본은 그 프로젝트의
  `etc/이미지백업-<날짜>/` 로 옮겨 둔다. 줄인 뒤 **빌드와 배포를 다시 해야** 화면에 반영된다
- **해시 없는 자산에 걸린 stale-while-revalidate**: `vercel.json` 을 고친다.
  주소에 내용 해시를 붙이거나 `max-age=0, must-revalidate` 로 바꾼다
- **쓰지 않는 크론**: 무엇을 부르는지 보고, 안 쓰면 뺀다

**고치지 않는 것.** 휴면 사이트, 등록 안 된 사이트, Vercel 프로젝트 삭제.
전부 보고에만 적는다. 지우는 것은 사람이 정한다.

### 4. 노션 페이지를 다시 적는다 (L1 로 만들고 노션에 쓴다)

노션 페이지: "각종 프로젝트 배포 링크".

이 페이지는 **윗부분만** 갈아끼운다. 아래쪽 "진행 상황 브리핑" 은 다른 업무가 쌓아 온
기록이라 손대지 않는다. 페이지를 통째로 덮어쓰면 그 기록이 조용히 바뀔 수 있다.

1. 페이지를 열어 **맨 위 callout 부터 "진행 상황 브리핑" 바로 앞까지**를 그대로
   `<OPS>/work/deploy-sync/notion-current-top.md` 에 저장한다.
   브리핑 제목이 그 파일에 들어가면 안 된다. 들어가면 스크립트가 멈춘다
2. 새 윗부분을 만든다

   ```bash
   node "<OPS>/manuals/deploy-sync/notion.mjs"
   ```

   `work/deploy-sync/notion-new.md` 가 생긴다. 링크는 `<DEV>/dev-hub/links.json` 에서,
   루프 숫자는 `loop-status.mjs` 에서, 배포 상태는 `scan.json` 에서 그 자리에서 가져온다.
   **숫자를 손으로 옮겨 적지 마라.** 옮겨 적으면 반드시 어긋난다
3. 노션에서 한 번 바꾼다. 찾아 바꾸기 한 번이다

   - 찾을 것: `notion-current-top.md` 내용 그대로
   - 바꿀 것: `notion-new.md` 내용 그대로

   문장이 안 맞으면 노션이 오류를 내고 **아무것도 안 바뀐다.** 그때는 페이지를 다시 받아
   1번부터 한다. 조용히 망가지는 것보다 시끄럽게 실패하는 쪽이 낫다
4. 페이지를 다시 열어 최종 동기화 시각이 오늘인지, 브리핑이 그대로 있는지 본다

링크판에 없는 링크가 노션에만 있으면 **`links.json` 에 넣고** 다시 만든다.
그냥 만들면 그 링크가 페이지에서 사라진다. 260825 에 약사 자체제품 조사판과
업무 자료 세 개가 그렇게 빠질 뻔했다.

노션을 못 만지는 런너면 2번까지만 하고 "본문은 만들어 뒀고 노션에 못 썼다" 를 보고에 적는다.

### 5. 링크판도 같이 굽는다 (L1)

노션과 공개 링크판은 같은 원장(`links.json`)을 본다. 한쪽만 고치면 서로 다른 말을 한다.

```bash
cd <DEV>/dev-hub && npm run deploy
```

`build.mjs` 는 `links.json` 이 있는 폴더에서 돌아야 한다. 다른 데서 부르면 파일을 못 찾는다.

### 6. 보고한다

무엇을 밀었고, 무엇을 안 밀었고, 무엇이 무거운지를 숫자로 적는다.

```

안 민 것: 휴면 8개, 사람이 부를 때만 1개

노션 갱신함. 링크판 다시 구움
```

## 잘못 올렸으면 되돌린다

**고쳐서 다시 올리려 하지 마라. 먼저 되돌리고 나서 고친다.**
사이트가 죽어 있는 시간이 짧을수록 좋고, 되돌리기는 2초면 끝난다.

```bash
node "<OPS>/manuals/deploy-sync/scan.mjs" --fast    # 안 해도 된다. 그냥 아래로 간다
```

1. 그 프로젝트의 배포 목록을 본다. 마지막으로 멀쩡했던 것을 고른다

   ```bash
   npx vercel ls <프로젝트> 2>&1
   ```

2. 그것을 프로덕션으로 다시 올린다. 새로 빌드하지 않으므로 빌드 시간이 안 든다

   ```bash
   npx vercel promote <그 배포 주소> --yes
   ```

3. 열어서 확인한다. 화면이 아니라 **자료 주소**를 확인해야 한다

   ```bash
   curl -sI <사이트>/<자료 파일> | head -3
   ```

되돌린 뒤에 원인을 본다. 되돌린 사실과 이유를 보고에 적는다.

## 알려진 함정

- **소스가 미커밋인 저장소를 그냥 올리면 남의 미완성이 프로덕션에 뜬다.**
  260825 에 `pharm-social-intelligence` 를 밀었는데, 다른 세션이 CSV 를 `public/data/` 에서
  `data/` 로 옮기는 작업을 하던 중이었다. 화면 코드는 아직 옛 주소를 부르고 있어서
  배포하자마자 자료가 404 가 됐다. `vercel promote` 로 나흘 전 배포를 되돌려 살렸다.
  그래서 `scan.mjs` 는 소스가 미커밋이면 자동 배포에서 뺀다.
  **판정이 "소스 미커밋" 으로 나오면 그 폴더에서 `git status` 를 눈으로 보고 정한다.**
  자료(`data/`, `state/`, `work/`)가 미커밋인 것은 루프가 도는 중이라 정상이다
- **동기화 명령이 자료를 새로 만들어 내는 것이면 절대 넣지 마라.**
  `zipgap-exchange` 의 `npm run build:data` 는 시드 추정치로 `listings.json` 을 다시 만든다.
  루프가 몇 주 동안 채운 실거래가 통째로 덮인다. 동기화 칸에는 **원장을 읽어 오는 것만** 적는다
- **`cd` 뒤에 `vercel` 을 이어 붙이면 엉뚱한 폴더에서 돈다.** `cd 어디 && ... && npx vercel --prod`
  로 한 줄에 이으면 vercel 이 그 폴더를 새 프로젝트로 잡아 만들어 버린다.
  260805 에 검증용 폴더가 통째로 공개 배포됐다. `run.mjs` 는 명령마다 cwd 를 따로 넘긴다.
  손으로 칠 때도 `cd` 는 별도 호출로 한다
- **`vercel project ls` 와 `vercel ls` 는 표를 stderr 로 뱉는다.** stdout 만 받으면 빈 문자열이 온다.
  `2>&1` 을 붙여야 파싱된다. 출력에 ANSI 색코드가 섞여 있어 지우고 봐야 한다
- **Vercel 은 마지막 배포를 "8m" "4d" 같은 나이로만 알려준다.** 분 단위로 비교하면
  방금 스스로 올린 루프를 매번 다시 밀게 된다. `registry.json` 의 유예분으로 막아 뒀다
- **`wellnessbox` 와 `etc/attendance` 는 push 로만 배포한다.** 여기서 `vercel --prod` 를 돌리면
  워킹트리째 올라가서 커밋 안 한 작업이 프로덕션에 잠깐 뜬다
- **저장소 밖 절대경로를 빌드가 읽으면 원격 빌드에서 죽는다.** `dev-hub` 와 `effect-pool` 이
  같은 함정에 빠졌다. 로컬에서는 통과하고 Vercel 에서만 ENOENT 로 죽어 실패 메일이 쏟아진다.
  정적 사이트는 `vercel.json` 의 `buildCommand` 를 빈 문자열로 두고 로컬에서 구운 `dist/` 를 올린다
- **정적 사이트를 다시 배포했는데 화면만 옛것이면 브라우저 캐시다.** `stale-while-revalidate`
  때문에 최대 하루 동안 옛 css 를 쓴다. 파일 이름에 해시가 없으면 반드시 이 사고가 난다.
  `weight.mjs` 가 이 조합을 찾아 준다
- **이름이 안 바뀌는 자료 파일에 `immutable` 을 걸면 새 자료가 영영 안 간다.**
  `pharm-social-intelligence` 가 `/data/(.*)` 에 `max-age=31536000, immutable` 을 걸어 뒀다.
  화면은 `/data/accounts.csv` 를 늘 같은 주소로 부른다. 한 번 열어 본 사람은 일 년 동안
  옛 자료를 본다. 동기화하고 배포해도 그 사람 화면은 그대로다.
  자료를 갈아끼우는 사이트는 `max-age=0, must-revalidate` 로 둔다. 304 라 싸다
- **배포한 뒤에는 화면이 아니라 자료 주소를 확인한다.** 첫 화면은 200 이 뜨는데
  자료만 404 인 경우가 실제로 있었다. `curl -sI <사이트>/<자료 파일>` 로 본다
- **`public/` 이 배포 payload 라고 단정하지 마라.** Next 프로젝트는 빌드 결과가 따로 나가고,
  `public/inbox` 처럼 사람이 넣어 둔 작업 파일이 섞여 있는 경우가 있다.
  `weight.mjs` 는 `.vercelignore` 를 반영하지만 그 밖은 사람이 눈으로 확인한다
- **그림을 줄이면서 확장자를 바꾸지 마라.** png 를 webp 로 바꾸면 이름이 달라져
  화면에서 그림이 통째로 사라진다. `shrink.mjs` 는 이름과 확장자를 그대로 둔다
- **`dist/` 만 줄이면 다음 빌드에 원래대로 돌아온다.** 원본이 있는 `public/` 을 줄여야 남는다
- **`zipgap-exchange` 는 push 안 한 커밋이 3만 개 넘는다.** 루프가 매 회차 커밋만 하고
  push 를 안 한다. 한 번에 밀면 오래 걸리니 사람이 정한다. 배포 자체는 CLI 라 push 와 무관하다
- **노션 페이지를 통째로 덮어쓸 때 브리핑을 먼저 떠 오지 않으면 날아간다.**
  `notion.mjs` 가 `notion-current.md` 를 못 찾으면 경고를 찍는다. 그 경고가 보이면 덮어쓰지 마라

## 사람에게 물어야 하는 지점

- Vercel 프로젝트 삭제. 되살릴 수 없다
- 등록 안 된 사이트를 새로 배포하거나 `registry.json` 에 넣는 것
- 커밋 수만 개를 한 번에 push 하는 것
- 봉인된 졸업논문 사이트의 숫자를 바꾸는 것

## 이 업무가 만지지 않는 것

- **진행 상황 브리핑.** 그건 `loop-briefing` 이 쓴다. 이 업무는 그 아래를 건드리지 않고 그대로 옮긴다
- **루프 자체.** 루프를 멈추거나 되살리지 않는다. 뒤처진 화면만 맞춘다
