# 릴스 조회수 나눠서 반복 주문하기

- **부르는 말**: 조회수 나눠서 넣어줘, 조회수 분할 주문, 조회수 반복 주문, 조회수 천천히 올려줘, 100회씩 100번 넣어줘, 조회수 드립, 조회수 묶음 상태 봐줘, snsview-drip
- **미리 허가**: snssupporter.com 에 사용자가 적어 준 수량과 횟수만큼 조회수 주문 (미리 충전한 잔액에서 차감, 카드 입력 없음). 숫자를 안 줬으면 100회 × 100번 × 5분 간격
- **런너**: either
- **제어층**: L1 로 전부 한다. API 키 발급 한 번만 사람이 화면에서
- **한 번에 걸리는 시간**: 시작까지 1분. 그 뒤 주문은 배경 프로세스가 (횟수 - 1) × 간격 동안 혼자 돈다. 100번을 5분 간격이면 8시간 15분

---

## 무엇을 만드는 업무인가

게시물 하나에 조회수를 한꺼번에 넣지 않고, 사용자가 정한 수량으로 잘게 나눠 일정 간격으로 반복 주문한다.
1만 회를 100회씩 100번, 5분마다 넣는 식이다. 끝나면 `<OPS>/work/snsview-drip/<묶음id>/state.json` 에
주문번호 100개가 남고, SNS서포터 주문내역에도 같은 링크로 100건이 찍혀 있다.

브라우저를 쓰지 않는다. SNS서포터 표준 API (`https://snssupporter.com/api/v2`) 를 셸 스크립트가 부른다.
에이전트 세션이 끝나도 배경 프로세스가 계속 돈다.

## 실행 계약

사용자가 이 업무를 호출하면 이 매뉴얼의 절차와 완료 검사를 한 번에 실행한다. 사용자가 링크와
수량, 횟수, 간격을 적어 시킨 것이 곧 그 금액에 대한 승인이다. 총액을 한 줄로 적고 그대로 시작한다.
주문 버튼을 사람에게 넘기지 않는다. 멈추는 것은 넷뿐이다. API 키가 없을 때, 잔액이 모자라
충전이 필요할 때, 링크가 이번에 시킨 것이 아닐 때, 매뉴얼 밖의 결제나 삭제가 끼어들 때.

## 쉬운 설명

### 쓰는 상황

릴스나 게시물의 조회수를 자연스럽게 올리고 싶을 때 씁니다. 한 번에 1만 회가 붙으면 티가 나니까
100회씩 100번, 5분마다 나눠 넣습니다. 몇 회씩, 몇 번, 몇 분 간격인지는 시킬 때 정합니다.

### 시키는 말

Claude 나 Codex 새 세션에 이렇게 말하면 됩니다.

> G드라이브 에이전트 폴더 참고해서 릴스 조회수 나눠서 반복 주문하기 업무 해줘.
> 링크 https://www.instagram.com/reel/XXXX/ 에 100회씩 100번, 5분 간격.

숫자를 빼면 100회씩 100번 5분 간격으로 넣습니다. 진행이 궁금하면 "조회수 묶음 상태 봐줘" 라고 하면 됩니다.

### 진행 순서

1. API 키가 있는지 봅니다. 처음 한 번은 사람이 SNS서포터 내 정보 화면에서 키를 발급받아 넣어 둡니다. 그 뒤로는 계속 됩니다.
2. 링크와 숫자를 정리하고 총액을 계산합니다. 100회씩 100번이면 1,000원입니다. 잔액과 끝나는 시각을 한 줄로 적습니다.
3. 주문을 시작합니다. 첫 주문은 바로 들어가고, 나머지는 배경에서 간격마다 하나씩 들어갑니다. 세션을 닫아도 계속 돕니다.
4. 첫 주문번호를 확인하고 묶음 이름과 끝나는 시각을 보고합니다.
5. 나중에 "상태 봐줘" 라고 하면 몇 번째까지 들어갔는지, 서버가 처리 중인지, 잔액이 얼마인지 보여줍니다.

### 결과물

SNS서포터 주문내역에 같은 링크로 횟수만큼 주문이 찍혀 있고, 조회수는 간격마다 조금씩 올라갑니다.
컴퓨터에는 묶음 폴더에 주문번호와 시각이 전부 남습니다.

### 사람이 직접 눌러야 하는 것

처음 한 번, API 키 발급입니다. SNS서포터 로그인 → 내 정보 → 환경 탭 → 새로고침 → 키 복사.
그다음 "키 복사했어" 라고 하면 에이전트가 클립보드에서 파일로 옮깁니다. 키 값은 화면에 안 찍습니다.
그 뒤로는 누를 것이 없습니다. 잔액이 모자라면 충전만 사람이 합니다.

## 채널과 계정

| 무엇 | 값 |
| --- | --- |
| 사이트 | https://snssupporter.com (계정 `dbwjtk`, 예비 계정은 드라이브 `자격증명/계정.md`) |
| API | `POST https://snssupporter.com/api/v2`, 표준 SMM 패널 API. 키는 `<DRIVE>/에이전트/자격증명/.env` 의 `SNSSUPPORTER_API_KEY` |
| 상품 | `813` `[동영상] 한국인 조회수🎥`. 1,000회에 100원 (1회 0.1원). 최소 50회 |
| 기본값 | 100회 × 100번 × 5분 = 1만 회, 1,000원, 8시간 15분 |

## 준비물

- `SNSSUPPORTER_API_KEY` 가 `.env` 에 있어야 한다. 아래 절차 1 로 확인한다
- 사용자가 준 게시물 링크. 릴스는 `https://www.instagram.com/reel/<코드>/` 꼴. 계정명이 낀 주소도 스크립트가 같은 꼴로 맞춘다
- 잔액. 총액보다 적으면 시작하지 않는다 (`--allow-short` 를 붙이면 잔액이 되는 데까지 돌고 멈춰 기다린다)

## 절차

1. **키가 있는지 본다 (L1)**
   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" check
   ```
   키, 잔액, 상품 단가와 최소 수량, 돌고 있는 묶음이 나오면 다음으로 간다.

   **키가 없으면 사람이 한 번 발급한다.** 에이전트는 발급 버튼을 못 누른다 (아래 함정).
   사람에게 이 세 줄을 그대로 준다.
   ```
   https://snssupporter.com/account 에서 환경 탭 → 새로고침 을 눌러 API 키를 발급받고 복사해 주세요.
   복사했으면 "키 복사했어" 라고 해 주세요. 제가 클립보드에서 파일로 옮깁니다.
   (키를 채팅에 붙여 주셔도 됩니다. 그러면 바로 넣습니다.)
   ```
   사람이 "복사했어" 라고 하면 이 명령으로 넣는다. **값을 화면에 찍지 않는다.**
   ```bash
   node "<OPS>/scripts/env-set.mjs" SNSSUPPORTER_API_KEY --clipboard
   ```
   채팅으로 키를 받았으면 표준입력으로 넣는다. `printf '%s' '<키>' | node "<OPS>/scripts/env-set.mjs" SNSSUPPORTER_API_KEY`
   넣고 나서 `check` 를 다시 돌려 잔액이 찍히는지 본다. 잔액이 찍히면 키가 맞는 것이다.

2. **입력값을 정리한다 (L1)**
   사용자 말에서 넷을 꺼낸다. 링크, 1회 수량(`--qty`), 총 횟수(`--runs`), 간격(`--every`).
   안 준 것은 기본값 100, 100, 5m 을 쓰고 보고에 "기본값으로 넣었다" 고 적는다.
   "1만 회를 100번" 처럼 총량으로 말하면 1회 수량 = 총량 ÷ 횟수 로 바꾼다. 1회 수량이 50 밑이면 못 넣는다.
   간격은 `5m`, `300s`, `1h`, 숫자만 쓰면 분이다. 60초 밑으로는 못 내린다.

3. **총액을 계산해 한 줄로 적는다 (L1)**
   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" plan --link <URL> --qty 100 --runs 100 --every 5m
   ```
   대상, 상품, 주문 구성, 비용과 잔액, 끝나는 시각이 다섯 줄로 나온다. **그대로 보고에 옮긴다.**
   답을 기다리지 않는다. 사용자가 숫자를 적어 시킨 것이 승인이다.
   잔액이 총액보다 적으면 여기서 멈추고 얼마 모자란지 적어 알린다. 충전은 사람이 한다.

4. **시작한다 (L1)**
   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" start --link <URL> --qty 100 --runs 100 --every 5m
   ```
   묶음 폴더 `<OPS>/work/snsview-drip/<묶음id>/` 가 생기고 배경 프로세스가 뜬다. 첫 주문은 바로 들어간다.
   `첫 주문 들어감: 주문번호 ...` 가 20초 안에 찍히면 성공이다. 안 찍히면 그 폴더의 `log.txt` 와 `run.err.txt` 를 본다.
   같은 링크로 돌고 있는 묶음이 있으면 시작을 거부한다. 겹쳐 넣을 이유가 분명할 때만 `--force`.

5. **보고한다 (L1)**
   묶음 id, 첫 주문번호, 총액과 잔액, 끝나는 시각, 상태 보는 명령을 적는다. 한 번에 다 적고 끝낸다.
   드라이브 `<DRIVE>/에이전트/보고/<날짜>-조회수분할.md` 에 `plan` 다섯 줄과 묶음 id 를 남긴다.
   배경 프로세스가 도는 동안 세션을 붙들고 있지 않는다. 끝날 때까지 기다리지 마라.

6. **"상태 봐줘" 라고 하면 (L1)**
   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" status            # 최근 묶음
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" status <묶음id> --api   # 서버 처리 상태와 잔액까지
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" list
   ```
   `끊김` 이면 프로세스가 죽은 것이다 (재부팅, 절전). `resume <묶음id>` 로 이어 간다. 들어간 회차는 다시 넣지 않는다.
   `멈춤: 잔액 부족` 이면 사람이 충전한 뒤 `resume`. 12회차 동안은 스스로 기다리다 그 뒤에 접는다.
   멈추라고 하면 `stop <묶음id>`. 15초 안에 멈춘다.

## 산출물

- `<OPS>/work/snsview-drip/<묶음id>/state.json`: 설정, 주문번호 목록, 오류, 진행 상태. 프로세스가 죽어도 여기서 이어 간다
- `<OPS>/work/snsview-drip/<묶음id>/log.txt`: 회차마다 한 줄. 주문번호, 수량, 금액, 잔액
- `<OPS>/work/snsview-drip/<묶음id>/plan.txt`: 시작할 때 적은 다섯 줄
- `<DRIVE>/에이전트/보고/<날짜>-조회수분할.md`: 사람이 보는 보고

## 완료 검사

- [ ] (기계) `checks.mjs`: 묶음 `state.json` 의 `done` 이 true 이고 `orders` 수가 `runs` 와 같다. 돌고 있는 중이면 진행률을 찍고 실패로 낸다
- [ ] (기계) `status --api` 에서 서버 상태가 `Completed` 나 `In progress` 로만 나온다. `error` 가 섞이면 그 주문번호를 본다
- [ ] (사람) https://snssupporter.com/orders 에 같은 링크로 횟수만큼 찍혀 있다. 겹쳐 들어간 회차가 없다

## 알려진 함정

- **사이트의 예약주문(드립피드)은 조회수 상품에 막혀 있다.** 주문 폼에서 `runs` 와 `interval` 칸이 숨겨져 있고 (260903, 260904 실측) API 서비스 목록의 `dripfeed` 도 꺼져 있다 → 그래서 이 스크립트가 한 건짜리 주문을 간격마다 나눠 넣는다. 사이트에서 한 번에 예약하려 들지 마라
- **API 키 발급 버튼(내 정보 → 환경 → 새로고침)은 에이전트가 못 누른다.** 260904 에 자동 모드 분류기가 그 클릭을 막았다. JS 로 폼을 제출하는 것도 같은 뜻이라 하지 않는다 → 사람이 한 번 누른다. 발급된 키는 그 카드에 표시된다
- **크롬 익스텐션의 JS 출력은 키처럼 생긴 문자열을 `[BLOCKED]` 로 가린다.** 화면 읽기로 키를 옮길 수 없다 → `env-set.mjs --clipboard` 로 사람이 복사한 값을 클립보드에서 파일로 바로 넣는다. 값이 대화에 안 남는다
- **키는 `.env` 에 넣고 화면에 찍지 않는다.** `check` 는 길이만 보여준다. 보고에도 값을 적지 마라
- **상품 813 의 최소 수량은 50 이다.** 100 은 된다. 1,000회에 100원이라 100회는 10원, 100번이면 1,000원. 260904 잔액이 1,032원이라 기본값 한 묶음이면 바닥난다. 두 번째 묶음 전에 충전이 필요하다
- **`start` 는 20초 동안 첫 주문을 지켜보고 돌아온다.** 그 뒤는 배경 프로세스 몫이다. 세션이 끝나도 산다 (260904 실측, Bash 도구가 끝난 뒤에도 자식이 24초를 다 돌았다). 재부팅하면 죽는다. `list` 에 `끊김` 으로 뜨니 `resume` 한다
- **주문 요청이 시간 초과로 실패하면 서버에는 들어갔을 수 있다.** 스크립트는 곧바로 다시 넣지 않고 한 회차를 기다린다. 완료 뒤 사람이 주문내역에서 겹친 회차가 없는지 본다. 이중 주문이 있었으면 `--runs` 를 하나 줄여 잡는다
- **자동 모드 분류기가 `start` 명령을 막으면** 그건 승인 문제다. `plan` 다섯 줄을 먼저 화면에 적고 다시 친다. 이 업무의 지출 허가 문장은 `설정/claude/settings.json` 의 `autoMode.allow` 에 있다
- **옛 방식(브라우저 주문)의 함정은 `shorts-pipeline` P7 에 있다.** 주문 페이지가 `/` 이고, 수량 칸을 폼 채우기로 넣으면 금액이 ₩0 에 머문다. API 가 막혔을 때만 그쪽으로 돌아간다
- **같은 링크에 사용자가 직접 넣은 별건이 섞일 수 있다.** 260903 에 1,000회짜리가 따로 있었다. 묶음 개수는 `state.json` 의 `orders` 로만 세고, 주문내역의 건수로 세지 마라

## 사람에게 물어야 하는 지점

- API 키가 없을 때. 발급은 사람이 한 번 누른다
- 잔액이 총액보다 적을 때. 충전은 사람이 한다
- 링크를 안 줬을 때. 링크 없이 시작하지 않는다
- 매뉴얼 밖의 결제, 삭제

## 묻지 말고 이렇게 한다

- 사용자가 숫자를 적어 시켰으면 그 숫자가 승인이다. `plan` 결과를 적고 `start` 까지 간다
- 숫자를 안 줬으면 100회 × 100번 × 5분으로 넣고 보고에 기본값이라고 적는다
- 세션을 붙들고 끝까지 기다리지 않는다. 첫 주문번호를 확인하면 보고하고 끝낸다
