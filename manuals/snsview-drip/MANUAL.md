# 릴스 조회수 나눠서 반복 주문하기

- **부르는 말**: 조회수 주문해줘, 조회수 분산 주문, 조회수 분할 주문, 조회수 나눠서 넣어줘, 조회수 나눠 넣어줘, 조회수 반복 주문, 조회수 천천히 올려줘, 조회수 올려줘, 100회씩 100번 넣어줘, 5분마다 조회수, 이 링크에 조회수, 조회수 드립, 조회수 묶음, 조회수 묶음 상태 봐줘, 주문 이어서 돌려줘, 새 릴스 올라오면 자동 주문, 릴스 감시, 릴스 감시 상태 봐줘, 자동 주문 꺼줘, reel-watch, snsview-drip
- **미리 허가**: snssupporter.com 에 사용자가 적어 준 수량과 횟수만큼 조회수 주문 (미리 충전한 잔액에서 차감, 카드 입력 없음). 숫자를 안 줬으면 100회 × 100번 × 5분 간격. 감시를 켜 둔 계정에 새 릴스가 올라오면 설정 파일에 적힌 수량으로 알아서 주문 (지금은 `kimjejo_pharma`, 릴스 하나에 ₩1,000, 하루 최대 2묶음)
- **런너**: either
- **제어층**: L1 로 전부 한다. API 키 발급 한 번만 사람이 화면에서
- **한 번에 걸리는 시간**: 시작까지 1분. 그 뒤 주문은 배경 프로세스가 (횟수 - 1) × 간격 동안 혼자 돈다. 100번을 5분 간격이면 8시간 15분

---

## 무엇을 만드는 업무인가

게시물 하나에 조회수를 한꺼번에 넣지 않고, 사용자가 정한 수량으로 잘게 나눠 일정 간격으로 반복 주문한다.
1만 회를 100회씩 100번, 5분마다 넣는 식이다. 끝나면 `<OPS>/work/snsview-drip/<묶음id>/state.json` 에
주문번호 100개가 남고, SNS서포터 주문내역에도 같은 링크로 100건이 찍혀 있다.

브라우저를 쓰지 않는다. SNS서포터 표준 API (`https://snssupporter.com/api/v2`) 를 셸 스크립트가 부른다.
에이전트 세션이 끝나도 배경 프로세스가 계속 돈다.

**쇼츠 업무의 조회수 주문과 헷갈리지 마라.** 사람이 링크와 함께 나누는 숫자(몇 회씩, 몇 번, 몇 분 간격)를
말했으면 이 업무다. 방금 올린 릴스에 2,000회를 한 번에 넣는 것은 `shorts-pipeline` 의 P7 이다.

## 실행 계약

사용자가 이 업무를 호출하면 이 매뉴얼의 절차와 완료 검사를 한 번에 실행한다. 사용자가 링크와
수량, 횟수, 간격을 적어 시킨 것이 곧 그 금액에 대한 승인이다. 총액을 한 줄로 적고 그대로 시작한다.
주문 버튼을 사람에게 넘기지 않는다. 멈추는 것은 넷뿐이다. API 키가 없을 때, 잔액이 모자라
충전이 필요할 때, 링크가 이번에 시킨 것이 아닐 때, 매뉴얼 밖의 결제나 삭제가 끼어들 때.

## 쉬운 설명

### 쓰는 상황

릴스나 게시물의 조회수를 자연스럽게 올리고 싶을 때 씁니다. 한 번에 1만 회가 붙으면 티가 나니까
100회씩 100번, 5분마다 나눠 넣습니다. 몇 회씩, 몇 번, 몇 분 간격인지는 시킬 때 정합니다.

### 시키는 말

Claude 나 Codex 새 세션에 이렇게 말하면 됩니다.

> G드라이브 에이전트 폴더 참고해서 릴스 조회수 나눠서 반복 주문하기 업무 해줘.
> 링크 https://www.instagram.com/reel/XXXX/ 에 100회씩 100번, 5분 간격.

숫자를 빼면 100회씩 100번 5분 간격으로 넣습니다. 진행이 궁금하면 "조회수 묶음 상태 봐줘" 라고 하면 됩니다.

### 새 릴스 자동 주문

김주성 대표님 계정(`kimjejo_pharma`)은 링크를 안 주셔도 됩니다. 새 릴스가 올라오면 컴퓨터가 알아서 100회씩 100번 넣습니다.
하루에 8번 봅니다. 대표님이 주로 올리시는 16~20시에는 17, 18, 19, 20시 정각에 보고, 나머지는 8, 12, 16, 23시에 봅니다.
주문을 넣으면 윈도우 알림이 뜹니다. 잔액이 모자라거나 확인이 두 번 연달아 실패해도 알림이 뜹니다.
멈추고 싶으면 "자동 주문 꺼줘", 요즘 어떤지 보려면 "릴스 감시 상태 봐줘" 라고 하면 됩니다.

### 진행 순서

1. API 키가 있는지 봅니다. 처음 한 번은 사람이 SNS서포터 내 정보 화면에서 키를 발급받아 넣어 둡니다. 그 뒤로는 계속 됩니다.
2. 링크와 숫자를 정리하고 총액을 계산합니다. 100회씩 100번이면 1,000원입니다. 잔액과 끝나는 시각을 한 줄로 적습니다.
3. 주문을 시작합니다. 첫 주문은 바로 들어가고, 나머지는 배경에서 간격마다 하나씩 들어갑니다. 세션을 닫아도 계속 돕니다.
4. 같이 지킴이를 걸어 둡니다. Claude 앱이 꺼지거나 컴퓨터를 다시 켜서 주문이 멈추면, 5분 안에 남은 회차부터 알아서 다시 시작합니다. 화면에는 아무것도 안 뜹니다. 다 넣고 나면 지킴이는 스스로 사라집니다.
5. 첫 주문번호를 확인하고 묶음 이름과 끝나는 시각을 보고합니다.
6. 나중에 "상태 봐줘" 라고 하면 몇 번째까지 들어갔는지, 서버가 처리 중인지, 잔액이 얼마인지 보여줍니다.

### 결과물

SNS서포터 주문내역에 같은 링크로 횟수만큼 주문이 찍혀 있고, 조회수는 간격마다 조금씩 올라갑니다.
컴퓨터에는 묶음 폴더에 주문번호와 시각이 전부 남습니다.

### 사람이 직접 눌러야 하는 것

처음 한 번, API 키 발급입니다. SNS서포터 로그인 → 내 정보 → 환경 탭 → 새로고침 → 키 복사.
그다음 "키 복사했어" 라고 하면 에이전트가 클립보드에서 파일로 옮깁니다. 키 값은 화면에 안 찍습니다.
그 뒤로는 누를 것이 없습니다. 잔액이 모자라면 충전만 사람이 합니다.

## 준비물

- `SNSSUPPORTER_API_KEY` 가 `.env` 에 있어야 한다. 아래 절차 1 로 확인한다
- 사용자가 준 게시물 링크. 릴스는 `https://www.instagram.com/reel/<코드>/` 꼴. 계정명이 낀 주소도 스크립트가 같은 꼴로 맞춘다
- 잔액. 총액보다 적으면 시작하지 않는다 (`--allow-short` 를 붙이면 잔액이 되는 데까지 돌고 멈춰 기다린다)

## 절차

1. **키가 있는지 본다 (L1)**
   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" check
   ```
   키, 잔액, 상품 단가와 최소 수량, 돌고 있는 묶음이 나오면 다음으로 간다.

   **키가 없으면 사람이 한 번 발급한다.** 에이전트는 발급 버튼을 못 누른다 (아래 함정).
   사람에게 이 세 줄을 그대로 준다.
   ```
   https://snssupporter.com/account 에서 환경 탭 → 새로고침 을 눌러 API 키를 발급받고 복사해 주세요.
   복사했으면 "키 복사했어" 라고 해 주세요. 제가 클립보드에서 파일로 옮깁니다.
   (키를 채팅에 붙여 주셔도 됩니다. 그러면 바로 넣습니다.)
   ```
   사람이 "복사했어" 라고 하면 이 명령으로 넣는다. **값을 화면에 찍지 않는다.**
   ```bash
   node "<OPS>/scripts/env-set.mjs" SNSSUPPORTER_API_KEY --clipboard
   ```
   채팅으로 키를 받았으면 표준입력으로 넣는다. `printf '%s' '<키>' | node "<OPS>/scripts/env-set.mjs" SNSSUPPORTER_API_KEY`
   넣고 나서 `check` 를 다시 돌려 잔액이 찍히는지 본다. 잔액이 찍히면 키가 맞는 것이다.

2. **입력값을 정리한다 (L1)**
   사용자 말에서 넷을 꺼낸다. 링크, 1회 수량(`--qty`), 총 횟수(`--runs`), 간격(`--every`).
   안 준 것은 기본값 100, 100, 5m 을 쓰고 보고에 "기본값으로 넣었다" 고 적는다.
   "1만 회를 100번" 처럼 총량으로 말하면 1회 수량 = 총량 ÷ 횟수 로 바꾼다. 1회 수량이 100 밑이면 못 넣는다.
   간격은 `5m`, `300s`, `1h`, 숫자만 쓰면 분이다. 60초 밑으로는 못 내린다.

3. **총액을 계산해 한 줄로 적는다 (L1)**
   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" plan --link <URL> --qty 100 --runs 100 --every 5m
   ```
   대상, 상품, 주문 구성, 비용과 잔액, 끝나는 시각이 다섯 줄로 나온다. **그대로 보고에 옮긴다.**
   답을 기다리지 않는다. 사용자가 숫자를 적어 시킨 것이 승인이다.
   잔액이 총액보다 적으면 여기서 멈추고 얼마 모자란지 적어 알린다. 충전은 사람이 한다.

4. **시작한다 (L1)**
   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" start --link <URL> --qty 100 --runs 100 --every 5m
   ```
   묶음 폴더 `<OPS>/work/snsview-drip/<묶음id>/` 가 생기고 배경 프로세스가 뜬다. 첫 주문은 바로 들어간다.
   `첫 주문 들어감: 주문번호 ...` 가 20초 안에 찍히면 성공이다. 안 찍히면 그 폴더의 `log.txt` 와 `run.err.txt` 를 본다.
   같은 링크로 돌고 있는 묶음이 있으면 시작을 거부한다. 겹쳐 넣을 이유가 분명할 때만 `--force`.

5. **보고한다 (L1)**
   묶음 id, 첫 주문번호, 총액과 잔액, 끝나는 시각, 상태 보는 명령을 적는다. 한 번에 다 적고 끝낸다.
   드라이브 `<DRIVE>/에이전트/보고/<날짜>-조회수분할.md` 에 `plan` 다섯 줄과 묶음 id 를 남긴다.
   배경 프로세스가 도는 동안 세션을 붙들고 있지 않는다. 끝날 때까지 기다리지 마라.

6. **"상태 봐줘" 라고 하면 (L1)**
   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" status            # 최근 묶음
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" status <묶음id> --api   # 서버 처리 상태와 잔액까지
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" list
   ```
   `끊김` 이면 프로세스가 죽은 것이다 (재부팅, 절전). `resume <묶음id>` 로 이어 간다. 들어간 회차는 다시 넣지 않는다.
   `멈춤: 잔액 부족` 이면 사람이 충전한 뒤 `resume`. 12회차 동안은 스스로 기다리다 그 뒤에 접는다.
   멈추라고 하면 `stop <묶음id>`. 15초 안에 멈춘다.

7. **끊겨도 스스로 되살아난다 (L1, 260905 추가)**
   `start` 와 `resume` 이 윈도우 예약 작업 `ops-snsview-drip-watch` 를 같이 건다.
   5분마다 깨어나 죽은 묶음을 남은 회차부터 다시 세우고, 되살릴 것이 없으면 **자기 예약을 스스로 지운다.**
   창은 안 뜬다. 상주하는 물건을 남기지 않는다.

   ```bash
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" guard            # 걸렸나, 다음 실행은 언제, 되살릴 묶음은 몇 개
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" watch            # 지금 바로 확인시킨다
   node "<OPS>/manuals/snsview-drip/scripts/snsview-drip.mjs" guard remove     # 예약을 손으로 걷는다
   ```

   `guard` 가 `안 걸려 있다` 인데 도는 묶음이 있으면 `guard install` 로 다시 건다.
   되살아나기까지 최대 5분이 빈다. 그 사이 회차는 건너뛴 것이 아니라 뒤로 밀린다.

## 새 릴스 자동 주문 (reel-watch, 260911 추가)

링크를 받지 않고 도는 갈래다. 감시를 켜 둔 계정에 새 릴스가 올라오면 스크립트가 위 절차 4 의 `start` 를 대신 부른다.
설정은 `<OPS>/manuals/snsview-drip/reel-watch.json` 하나다.

| 칸 | 지금 값 | 뜻 |
| --- | --- | --- |
| `account` | `kimjejo_pharma` | 감시할 계정 |
| `checkTimes` | 08, 12, 16, 17, 18, 19, 20, 23시 | 매일 이 시각에 한 번씩 본다. 하루 8번 |
| `order` | 100회 × 100번, 5분 간격 | 릴스 하나에 넣는 주문. ₩1,000 |
| `dailyMax` | 2 | 하루에 새로 시작하는 묶음 한도 |
| `maxAgeHours` | 72 | 올라온 지 이보다 오래된 릴스는 안 넣고 알림만 띄운다 |
| `failAlertAfter` | 2 | 확인이 2번 연달아 실패하면 알림. 그 뒤로는 하루 한 번 |

**확인 시각은 사람이 정했다 (260911).** 대표님 최근 릴스 10개가 전부 평일 16:47~19:00 에 올라왔다.
그래서 그 시간대는 1시간마다 보고 나머지는 4시간 안팎으로 벌렸다. 1시간 늦게 들어가는 것은 괜찮다고 했다.
처음 제안한 5분, 15분, 1시간 간격(하루 104번)은 "너무 과하다" 로 반려됐다. **확인 횟수를 늘리는 쪽으로 바꾸지 마라.**
시간대 밖에 올려도 놓치지 않는다. "지난번 목록에 없던 릴스" 를 찾으니 다음 확인에서 잡는다. 늦게 잡힐 뿐이다.

```bash
node "<OPS>/manuals/snsview-drip/scripts/reel-watch.mjs" status       # 예약, 마지막 확인, 오늘 주문 수, 최근 새 릴스
node "<OPS>/manuals/snsview-drip/scripts/reel-watch.mjs" tick --dry   # 지금 읽고 무엇을 할지만 찍는다. 아무것도 안 바꾼다
node "<OPS>/manuals/snsview-drip/scripts/reel-watch.mjs" install      # 예약을 걸고 곧바로 한 번 본다. checkTimes 를 바꿨으면 다시 친다
node "<OPS>/manuals/snsview-drip/scripts/reel-watch.mjs" remove       # 끈다. 상태와 기록은 남는다
```

한 번 확인에서 하는 일은 이렇다.

1. 로그인 없는 헤드리스 크롬으로 프로필 첫 화면을 연다 (L1, 8초쯤). 타일 12개가 `/<계정>/reel/<코드>/` 꼴로 읽힌다
2. 본인 릴스만 남긴다. 캐러셀과 사진(`/p/`), 다른 계정이 올린 협업 게시물은 뺀다
3. 처음 확인이면 지금 있는 릴스를 전부 본 것으로 적고 끝낸다. **켜기 전 릴스는 주문하지 않는다**
4. 본 적 없는 릴스가 있으면 최근 것부터 차례로 거른다
   - 켜기 1시간 전보다 먼저 올라온 릴스면 안 넣는다. 고정을 풀거나 보관을 풀어서 다시 보인 옛 릴스다
   - `work/snsview-drip/` 에 같은 코드의 묶음이 있으면 안 넣는다. 사람이 이미 시킨 것이다
   - 올라온 지 72시간이 넘었으면 안 넣고 알림을 띄운다
   - 오늘 이미 2묶음을 넣었으면 보류하고 알림을 띄운다. 내일 확인에서 넣는다
   - 다 통과하면 `snsview-drip.mjs start` 를 부른다. 잔액 확인, 겹침 방지, 배경 루프, 되살리기 예약은 전부 `start` 가 맡는다
5. 주문을 시작했으면 윈도우 알림을 띄우고 드라이브 `보고/<날짜>-조회수분할.md` 에 이어 붙인다

알림은 주문 시작, 잔액 부족, 하루 한도 보류, 너무 오래된 릴스, 첫 회차 멈춤, 확인 연속 실패에서 뜬다.
같은 릴스에 같은 사유면 한 번만 뜬다. 잔액 부족은 사람이 충전하면 다음 확인이 알아서 넣는다.

상태는 `<OPS>/work/reel-watch/<계정>/state.json`, 기록은 같은 폴더의 `log.txt` 다. 예약 이름은 `ops-reel-watch`.

- **"릴스 감시 상태 봐줘"** 라고 하면 `status` 결과를 그대로 옮긴다
- **"자동 주문 꺼줘"** 는 `remove`, **"다시 켜줘"** 는 `install` 이다
- **감시 계정 릴스 링크를 주며 "감지 안 됐으면 지금 넣어 줘"** 라고 하면 `status` 의 최근 새 릴스부터 본다. 묶음이 이미 있으면 새로 넣지 않고 `snsview-drip.mjs status <묶음id> --api` 결과를 옮긴다
- 감시 계정이나 시각을 바꾸라고 하면 `reel-watch.json` 을 고치고 `install` 을 다시 친 뒤 커밋한다. 계정을 바꾸면 그 계정은 처음 확인부터 다시 센다

## 알려진 함정

- **사이트의 예약주문(드립피드)은 조회수 상품에 막혀 있다.** 주문 폼에서 `runs` 와 `interval` 칸이 숨겨져 있고 (260903, 260904 실측) API 서비스 목록의 `dripfeed` 도 꺼져 있다 → 그래서 이 스크립트가 한 건짜리 주문을 간격마다 나눠 넣는다. 사이트에서 한 번에 예약하려 들지 마라
- **API 키 발급 버튼(내 정보 → 환경 → 새로고침)은 에이전트가 못 누른다.** 260904 에 자동 모드 분류기가 그 클릭을 막았다. JS 로 폼을 제출하는 것도 같은 뜻이라 하지 않는다 → 사람이 한 번 누른다. 발급된 키는 그 카드에 표시된다
- **크롬 익스텐션의 JS 출력은 키처럼 생긴 문자열을 `[BLOCKED]` 로 가린다.** 화면 읽기로 키를 옮길 수 없다 → `env-set.mjs --clipboard` 로 사람이 복사한 값을 클립보드에서 파일로 바로 넣는다. 값이 대화에 안 남는다
- **키는 `.env` 에 넣고 화면에 찍지 않는다.** `check` 는 길이만 보여준다. 보고에도 값을 적지 마라
- **상품 813 의 최소 수량은 100 이다 (260909 실측).** 260904 에는 50 이었는데 판매자가 올렸다. 기본값 100회는 그대로 되지만 그보다 잘게 쪼갤 수는 없다. `check` 가 찍는 최소 수량을 그때그때 믿는다. 1,000회에 100원이라 100회는 10원, 100번이면 1,000원. 260904 잔액이 1,032원이라 기본값 한 묶음이면 바닥난다. 두 번째 묶음 전에 충전이 필요하다
- **`start` 는 20초 동안 첫 주문을 지켜보고 돌아온다.** 그 뒤는 배경 프로세스 몫이다. 세션이 끝나도 산다 (260904 실측, Bash 도구가 끝난 뒤에도 자식이 24초를 다 돌았다)
- **Claude 앱이 꺼지면 배경 프로세스도 같이 죽는다 (260905 실측).** 앱 자동 업데이트가 자기를 껐는데 36회차에서 주문이 멈춰 있었다. `detached` 로 띄워도 앱이 만든 작업 개체(job object)에 묶여 있어서 함께 끌려간다. **그래서 되살리기를 앱 바깥(윈도우 예약 작업)에 뒀다.** 예약 작업이 5분마다 확인해 다시 세운다. 재부팅과 절전에도 같은 길로 돌아온다
- **되살릴 때 곧바로 주문하면 `neworder.error.link_duplicate` 로 되돌아온다 (260905 실측).** 같은 링크에 연달아 넣어서다. 돈은 안 나가지만 한 회차를 버린다. 그래서 이어 받을 때는 직전 주문 시각에 간격을 더한 때부터 넣는다
- **죽었는지 pid 로만 보면 틀린다.** 윈도우가 죽은 pid 를 다른 프로그램에 다시 내준다. 상태 파일에 심장박동(`heartbeatAt`)을 15초마다 찍고 그게 낡았으면 죽은 것으로 본다. 심장박동을 안 찍던 옛 상태 파일은 `nextAt` 이 한참 지났는지로 가늠한다
- **로그온 트리거에 사용자를 안 적으면 예약이 안 걸린다.** `schtasks` 가 `액세스가 거부되었습니다` 로 되돌아온다. 모든 사용자에게 걸리는 트리거라 관리자 권한이 필요해서다. `<LogonTrigger>` 안에 `<UserId>` 를 넣으면 그냥 걸린다 (260905 실측)
- **`schtasks /Create /XML` 은 UTF-16 파일만 읽는다.** UTF-8 로 쓰면 XML 이 잘못됐다고 되돌아온다
- **Git Bash 에서 `schtasks /Query` 를 치면 `/Query` 가 경로로 바뀐다.** MSYS 가 슬래시로 시작하는 인자를 경로로 고쳐서다. 셸에서 직접 치지 말고 스크립트의 `guard` 명령을 쓴다
- **예약 작업이 되살린 프로세스는 이 창의 환경변수를 안 물려받는다.** 되살리기를 시험할 때는 묶음 상태 파일의 `apiUrl` 에 로컬 주소를 적어 둔다. 진짜 주문이 새지 않게 `127.0.0.1` 과 `localhost` 만 받는다
- **주문 요청이 시간 초과로 실패하면 서버에는 들어갔을 수 있다.** 스크립트는 곧바로 다시 넣지 않고 한 회차를 기다린다. 완료 뒤 사람이 주문내역에서 겹친 회차가 없는지 본다. 이중 주문이 있었으면 `--runs` 를 하나 줄여 잡는다
- **자동 모드 분류기가 `start` 명령을 막으면** 그건 승인 문제다. `plan` 다섯 줄을 먼저 화면에 적고 다시 친다. 이 업무의 지출 허가 문장은 `설정/claude/settings.json` 의 `autoMode.allow` 에 있다
- **옛 방식(브라우저 주문)의 함정은 `shorts-pipeline` P7 에 있다.** 주문 페이지가 `/` 이고, 수량 칸을 폼 채우기로 넣으면 금액이 ₩0 에 머문다. API 가 막혔을 때만 그쪽으로 돌아간다
- **같은 링크에 사용자가 직접 넣은 별건이 섞일 수 있다.** 260903 에 1,000회짜리가 따로 있었다. 묶음 개수는 `state.json` 의 `orders` 로만 세고, 주문내역의 건수로 세지 마라
- **로그아웃 조회 API 는 막혀 있다 (260911 실측).** `web_profile_info` 는 브라우저 헤더를 다 붙여도 첫 요청부터 429 였다. 프로필과 게시물 페이지를 그냥 받아 오면 200 이지만 스크립트만 든 껍데기라 og 태그도 게시물 목록도 없다 → `reel-watch` 는 헤드리스 크롬으로 프로필을 연다. 로그아웃으로도 타일 12개가 붙는다
- **게시물 코드에 올린 시각이 들어 있다.** 코드를 64진수로 풀어 id 를 만들면 `(id >> 23) + 1314220021721` 이 올린 시각(ms)이다. 260911 에 릴스 페이지 `time[datetime]` 두 건과 분까지 맞았다. 옛 릴스 거르기와 "올라오고 몇 분 뒤 잡았나" 를 요청 없이 이걸로 계산한다
- **예약 작업의 시간 제한은 `reel-watch` 에 안 먹는다.** 예약이 띄우는 것은 `hidden-run.vbs` 를 도는 wscript 이고, wscript 는 node 를 띄우자마자 빠진다 → 시간 제한(8분)과 겹침 잠금(`tick.lock`)을 스크립트 안에 뒀다
- **확인 시각을 오늘 날짜로 걸면 이미 지난 시각이 곧바로 한 번 돈다.** `StartWhenAvailable` 이 놓친 실행으로 치기 때문이다 → 지난 시각은 내일 날짜로 건다
- **자동 주문은 사이트 주문내역을 못 본다.** 표준 API 에 주문 목록을 받는 명령이 없다. 겹침은 `work/snsview-drip/` 의 묶음으로만 가린다 → 감시 중인 계정의 릴스는 사이트에서 손으로 넣지 말고 에이전트에게 시킨다. 그래야 묶음이 남아서 두 번 안 나간다
- **컴퓨터가 꺼져 있으면 확인도 없다.** 켜지면 놓친 예약이 한 번 돌아서 그때 잡는다. 올라온 지 72시간이 넘었으면 넣지 않고 알림만 띄운다
- **윈도우 알림은 PC 앞에 있어야 보인다 (260911 실측).** 17:28 에 올라온 대표님 릴스를 18:00 확인에서 잡아 주문을 시작했는데, 사람은 자리에 없어서 몰랐다. 18:15 에 같은 링크를 주며 "아직 감지 안 됐지? 지금 바로 주문해 달라" 고 시켰다 → 감시 계정 링크를 받으면 `reel-watch.mjs status` 부터 본다. 이미 돌고 있으면 넣지 않고 진행을 보고한다. `start` 가 같은 링크의 겹침을 막지만 `--force` 를 붙이면 두 번 나간다

## 사람에게 물어야 하는 지점

- 잔액이 총액보다 적을 때. 충전은 사람이 한다

- 세션을 붙들고 끝까지 기다리지 않는다. 첫 주문번호를 확인하면 보고하고 끝낸다
